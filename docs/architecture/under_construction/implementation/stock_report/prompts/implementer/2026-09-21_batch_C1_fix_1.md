## Part 1 — production defects (do these first)

**B1 — blocking. The creation path accepts soft-deleted items and tasks.**
`_phase3_reason` in `create_stock_task_assignments.py` checks `row is None or row.is_deleted` for
the stock-report row, but only `task is None` and `item is None` for the other two — and
`_locks.py:_lock` filters on `workspace_id` and `client_id` only, so a soft-deleted Task or Item
is returned and passes. The intention's **MC-16 predicate table** requires both, verbatim:
`Item lookup (processed, creation, guard) → items.is_deleted = false` and
`Task lookup (creation) → tasks.is_deleted = false`.

Consequence today: assigning a deleted item creates the assignment, raises the row's
`quantity_in_queue` by its quantity, and flips the deleted task's `is_stock_assignment` back on —
with no hook left to clean up, because the deletion already ran.

Fix it **in `create_stock_task_assignments.py`'s phase-3 checks**, not in `_lock`. `_lock` is
phase 3's approved shared helper used by other callers with different needs; changing it is
out of perimeter and would be a §9 rule 17 relocation. Return `task_not_found` /
`item_not_found` respectively, keeping MC-13's existing reason order.

**Two new criterion rows are already authored for this: plan 8 C1(v) (deleted task) and C1(w)
(deleted item).** Build and arm both.

**B2 — blocking. A repeated id in a delete double-subtracts, silently.**
`delete_stock_task_assignments.py` sets `ids = request.client_ids` and then loops
`for client_id in sorted(ids)`. The missing-check above it *is* deduplicated
(`sorted(set(missing))`); the loop is not. A request naming the same assignment twice calls
`remove_assignment` twice on the same object and subtracts its quantity twice. The counter never
goes negative, so §12A's inline repair never fires and nothing is logged.

**Owner ruling: de-duplicate, do not refuse.** Deletion is idempotent; a refusal would fail an
honest retry, and a multi-select listing one row twice is not the user's error. **Apply the
de-duplication once, at the top**, so the missing-check, the removal loop and the response all
read the same set — deduping in one place and not another is precisely this defect. The response
lists each id once, sorted.

**Criterion row C6(j) is already authored for this.** Build and arm it.

**S1 — should-fix. Unknown fields are accepted over HTTP.**
The router's body models (`_CreateStockTaskAssignmentsBody`, `_DeleteStockTaskAssignmentsBody`)
carry no `extra="forbid"`, so MC-13's "unknown fields → 422" is unmet on the real HTTP surface —
the strictness sits one layer deeper than any client can reach. Add `ConfigDict(extra="forbid")`
to the router body models (the reviewer counted three). Keep the command-level behaviour as is.
