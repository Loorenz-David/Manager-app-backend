## 3. B2 (blocking) — the guard wedges the suite; make create-and-mark atomic

**Reproduced by the coordinator, mechanism exact.** A database created with
`CREATE DATABASE … TEMPLATE beyo_test_template` inherits the template's marker row, whose
`database_name` column reads `beyo_test_template`. `_marker_present_on_connection` requires
`marker_key = $1 AND database_name = $2`, so the new worker database reports
`marker_present = False` and `assert_disposable_database` **refuses to drop it — permanently.**
Measured directly: on a database created from the template, the guard's own predicate returns
`0`.

Compounded by two things: `start()`'s cleanup is `except Exception`, which does **not** catch the
`KeyboardInterrupt` a developer uses to stop a slow suite; and the cleanup is `best_effort=True`,
which swallows the guard's refusal silently. The result is that an interrupted run strands
`beyo_test_main` and **every later pytest invocation aborts** with
`UnsafeDatabaseError: Database lacks the disposable marker` until a human drops it by hand.

**Fix it.** The reviewer offers two shapes and either is acceptable: set the marker in the same
step that creates the database, or let the drop guard accept a marker row whose `marker_key`
matches regardless of `database_name` (that row can only exist because this code wrote it).
State which you chose and why. Handle `KeyboardInterrupt` on the cleanup path.

**Do not weaken the guard to achieve this.** The four fail-closed conditions — name pattern,
not-the-configured-database, marker present, URL parses — all stay. C2 must still pass unchanged.

**Extend C8 with the row it is missing.** Its current row marks the leftover with its *own* name
before asserting reabsorption, so it exercises the easy half and cannot see this defect. Add a
row that leaves a database behind **without** re-marking it — that is the named mutation this
criterion needs, and it must turn C8 red before your fix and green after. Record both sides.
