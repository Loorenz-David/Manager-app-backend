## 1. F-1 — the production bug. Do this first.

`app/beyo_manager/services/commands/stock_report/sync_task_stock_assignments.py`, the step-3
discovery query. It reads:

```python
assignment = await session.scalar(
    select(StockTaskAssignment).where(
        StockTaskAssignment.workspace_id == workspace_id,
        StockTaskAssignment.task_id == task.client_id,
        StockTaskAssignment.is_deleted.is_(False),
    )
)
```

Two halves of intention **§5B MC-2 step 3** were dropped: the
**`state.in_(ACTIVE_ASSIGNMENT_STATES)` predicate**, and **`scalar_one_or_none()`** in place of
`scalar`.

**Why this is a real defect and not a style point.** The intention says the partial unique index
`uix_stock_task_assignments_task_active` is what lets MC-2 *"read with `scalar_one_or_none()` and
never have to choose among several"* — and that index's predicate is
`WHERE is_deleted = false AND state IN ('in_queue','in_progress','awaiting')`. **The uniqueness
exists only inside the active-state predicate.** Drop the state filter and the query spans
terminal rows, where the index guarantees nothing, and `scalar` silently returns whichever row
the database hands back first.

A task legitimately carries a terminal assignment **and** a live one (§14F F1: a terminal
assignment does not block a new one; 8A's `_SCANNER_PROCESSED_STATES` means `failed` does not
block re-assignment; plan 10 C3(b)'s X1 path un-fails the task). When discovery returns the
terminal one, the post-lock terminal skip fires and **the live assignment never syncs — on this
and every future state change, with no error anywhere.** The reviewer reproduced it.

**Fix:** restore both halves. **Keep the post-lock terminal skip** — C5(a) and C5(c) need it, and
it is doing a different job (guarding against a state change between discovery and lock).

**Rule 16 applies:** `ACTIVE_ASSIGNMENT_STATES`, never a spelled list.

Its row is **plan 10 C1(m)**, new and owed (below).
