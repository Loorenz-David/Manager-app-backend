## 1. Production-code corrections (six sites)

These are real divergences from the contract. Fix the code, then arm the row that should have
caught it.

**F-B1 (blocking) — `repair_stock_report` crashes on the divergence it must fix.**
`repair_stock_report.py:38-54` selects only rows with `priority IS NOT NULL`, and the main loop
`continue`s on both ordering kinds (`:171-172`). A row with `priority = NULL` and
`priority_order = 1` is repaired by nobody, the post-repair re-check (`:215-224`) still sees it, and
the whole transaction rolls back — so a workspace holding one such row can never be repaired at all
and every other divergence in it is abandoned. Reproduced verbatim as probe P10.
Handle `expected is None` **before** `_repair_priority_orders`: set `priority_order = NULL` and
write one `stock_report_item` repair record whose `stored_value` is the old order and whose
`recomputed_value` is NULL. Authority: intention §12A MC-20's repair table, plan 3 C1(h) and C3(h).
Then implement plan 3 C3(h)'s row as written.

**F-B2 (blocking) — `normalize_stock_criteria` keeps blank list elements.**
MC-3's value table filters them: `sorted({e.strip().lower() for e in v if e.strip().lower() != ""})`.
`criteria_normalization.py:17` has no filter, so `{'k': ['Teak', '  ', 'Dark']}` normalizes to
`['', 'dark', 'teak']` instead of `['dark', 'teak']`. That changes `properties_signature`, so the
same rule lands on a different `stock_report_item` identity and the matcher carries a `""` token no
item value can satisfy. Add the filter. Keep the version constant at `1` (§0.1) and update the
golden vectors. Plan 1's C4 value table has no row for a list mixing blank and non-blank elements —
**do not edit the criteria table**; add the test and declare the missing row as a candidate
criterion in plan 1's Review log (see §5).

**F-S1 — the derived `wood_group` is lower-cased, diverging from Scanner.**
`scanner_property_tables.py:47` returns `group.lower()`; Scanner's
`groupByMember.set(normalizeMember(member), group)` stores the group name **as declared** and
returns `"Dark"`, `"Teak"`, `"Light"`. The reviewer confirmed this against Scanner itself (review
§3.2). Plan 2 C2(h), C4(a), C4(b) and C4(d) all state the capitalized value; the tests at
`test_criteria_matcher.py:76,88` assert the lower-cased one, cementing the divergence. Return
`group` unchanged and update those assertions to the plan's literals. Nothing is user-visibly wrong
today because both sides tokenize to lower case — but `build_item_property_bag` is a §6.1 public
name and the next consumer comparing a bag value to a Scanner value will disagree.

**F-S2 — the nullness `expected` is `len(assigned) + 1`, not `max(group) + 1`.**
`consistency.py:121-126`. Intention §12A and master plan §6.5 both say `max + 1`. They agree only on
a dense group; probe P5 on a `[1, 7]` group reported 3 where the contract says 8. The *repaired*
value is right (density renumbering makes it so) — it is the number the admin is shown that is
wrong. Use `max(assigned_orders, default=0) + 1`. Restore plan 3 C1(g)'s dense `[1, 2]` fixture
**and** add the sparse case as the discriminating neighbour, so the row can tell `max+1` from
`len+1`.

**F-S6 — the goal-total repair writes `stock_report_history_records` unlocked.**
§12A's repair lock order is "advisory → tasks → rows → assignments → **history records** — each
class ascending". `repair_stock_report.py:182-189` issues an absolute
`UPDATE … SET quantity_awaiting = …` on a row that was never locked, and `_locks.py` has no history
helper. Two manual repairs are serialized by the advisory lock, but phase 5's inline goal credit
will not take it, so a manual repair can overwrite a concurrent credit with a stale absolute value.
Add `lock_stock_report_history_records` to `_locks.py` and lock the diverging records after the
assignments. **Report the new helper's signature in your handoff** — I add it to master plan §6.5;
do not edit the master plan yourself.

**F-S7 — no "≠ 1 row is a programming error" guard on three of four repair statements.**
Plan 3 §7 makes this a structural check. `set_task_stock_flag` (`_task_flag.py:14-15`) checks
`rowcount not in (0, 1)` and so accepts 0, which on the repair path means the repair silently did
nothing. The counter UPDATE (`repair_stock_report.py:191-201`), the goal-total UPDATE (`:183-189`)
and the priority-order UPDATE (`:71-79`) have no rowcount check at all. Assert `rowcount == 1` on
all four **repair-path** statements; the flag's idempotent 0 case stays legitimate outside the
repair path.
